# Wikipedia Interest Analyzer

Навичка агента, яка дозволяє AI-асистенту аналізувати перегляди Wikipedia, щоб
допомогти засновникам B2C-застосунків зрозуміти, чи зростає інтерес до теми і
наскільки цьому зростанню можна довіряти — результат подається як PDF-звіт на
одну сторінку.

## Для кінцевого користувача (засновник, що спілкується з AI-агентом)

Навичка відповідає формату Agent Skills: каталог з `SKILL.md` та кодом, який
сумісний AI-агент може виявити й використовувати самостійно. Ми будували й
перевіряли її саме на **Claude Code**. Зробіть symlink каталогу цієї навички
у папку skills вашого проєкту, і Claude Code підхопить її автоматично — без
додаткового налаштування:
```bash
ln -s /path/to/wikipedia-interest /your/project/.claude/skills/wikipedia-interest
```

(Конвенція Agent Skills — автоматичне виявлення
`SKILL.md` у каталозі skills — специфічна саме для Claude Code / claude.ai;
інші AI-продукти не сканують файли таким чином. Сам вміст `SKILL.md` не
прив'язаний до Claude, тож інший агент з підтримкою інструментів у принципі
міг би отримати ці інструкції вручну, але це не перевірялося. Вимогу "працює
на дешевій/швидкій моделі" ми перевіряли, підміняючи саме модель — а не
середовище агента — запускаючи безкоштовні моделі на кшталт NVIDIA Nemotron
через Claude Code через локальний проксі.)

Після встановлення жодних команд запускати не потрібно — ви говорите з агентом
звичайною мовою, наприклад:

> "Ми думаємо додати курс з астрономії до освітнього застосунку. Чи зростає
> інтерес до цієї теми в україномовній Wikipedia за останні 2 роки, і наскільки
> цьому зростанню можна довіряти?"

Агент:
1. Визначить точну назву статті Wikipedia для кожної запитаної мови (через
   Wikidata). Якщо впевненого збігу немає — запитає вас підтвердити або надати
   точну назву статті.
2. Отримає дані про перегляди й порахує тренд, зростання та рівень довіри
   (`high`/`medium`/`low`) з поясненнями звичайною мовою.
3. Відповість коротким вердиктом вашою мовою і згенерує PDF-звіт на одну
   сторінку з графіком і тими ж цифрами, збережений локально.
4. Можна уточнювати запит природно — "додай польську", "зроби 3 роки", "чому
   низька довіра?" — без повторного виконання вже кешованої роботи.

Решта цього README — для розробників: як побудована навичка, як запускати її
напряму та як вона перевірялася.

## Огляд

Навичка отримує дані про перегляди Wikipedia, визначає відповідну статтю для
кожної мови через Wikidata, обчислює нормалізовані метрики (річне зростання,
стійкий до сезонності тренд, виявлення сплесків), оцінює надійність результату
і генерує PDF-звіт на одну сторінку. Керується AI-агентом через невеликий
набір CLI-команд з виводом у JSON (див. `SKILL.md` для робочого процесу
агента).

**Що працює сьогодні:**
- Визначення точної назви статті для кожної мови через Wikidata, з ручним
  перевизначенням (`spec.articles`) на випадок, якщо визначення неоднозначне
  або помилкове.
- Отримання щоденних переглядів для статті, з кешуванням на диску.
- Обчислення річного зростання (сирого й нормалізованого), стійкого до
  сезонності тренду (нахил Тейла-Сена на ковзній 12-місячній сумі), виявлення
  сплесків (робастний z-score), і рівня довіри `high`/`medium`/`low` з
  поясненнями звичайною мовою, англійською або українською (`report_lang`).
- Генерація PDF-звіту A4 на одну сторінку з графіком, таблицею метрик і
  поясненнями довіри, підписаних мовою звіту.
- Виконання повного циклу для однієї або кількох мов з файлу специфікації
  (`run --spec`).

**Відоме обмеження:** кілька мов в одному `run` досі аналізуються незалежно,
окремий звіт на кожну мову — поки немає спільного рейтингу чи порівняльного
графіка між мовами (заплановано наступним, див. Roadmap).

## Встановлення

```bash
cd wikipedia-interest
uv sync
```

## Використання

### CLI-команди

Запускайте через `uv run wikitrends <command>` з каталогу `wikipedia-interest`.
Кожна команда виводить один JSON-об'єкт у stdout: `ok`, `data`, `warnings[]`,
`next_step`. Коди виходу: `0` успіх, `2` неправильний ввід, `3` проблема
даних/API.

| Команда | Призначення |
|---|---|
| `fetch` | Завантажити щоденні перегляди для однієї статті одного мовного розділу. |
| `analyze` | Обчислити метрики й надійність з кешованих даних. |
| `report` | Згенерувати PDF на одну сторінку з результату `analyze`. |
| `run --spec spec.json` | Визначення статті + fetch + analyze + report для однієї або кількох мов. |

Поля `spec.json`:
- `topic` (обов'язково): тема будь-якою мовою — визначається через Wikidata
  для кожної цільової мови.
- `languages` (обов'язково): список кодів мов, наприклад `["uk", "pl"]`.
- `window`: `[start, end]` у форматі `YYYYMMDD`.
- `articles` (опційно): `{"uk": "Точна назва"}` — пропускає визначення через
  Wikidata для цієї мови й використовує вказану назву напряму. Використовуйте,
  коли визначення не спрацювало або ви вже знаєте точну назву.
- `report_lang` (опційно, за замовчуванням `"en"`): `"en"` або `"uk"` — мова
  PDF-звіту, пояснень надійності та вердикту.

`data` у відповіді `analyze` містить:
- `metrics`: `yoy_raw`, `yoy_norm`, `yoy_ex_spikes`, `trend_pct_per_year`,
  `spike_share`, `spike_days`, `volume` (`median_daily_12m`, `total_12m`),
  `first_seen`, `young_article`, `basket_consistency`, `months`.
- `reliability`: `confidence` (`high`/`medium`/`low`), `flags`, `reasons`.
- `headline`: одне речення-вердикт, що поєднує напрямок, величину й довіру.

### Приклад

```json
{
  "topic": "astronomy",
  "languages": ["uk"],
  "window": ["20240901", "20260801"],
  "report_lang": "uk"
}
```
```bash
uv run wikitrends run --spec spec.json
```
Тема тут англійською — визначення саме й знаходить українську статтю
(`Астрономія`) автоматично. Якщо визначення неоднозначне або не спрацювало для
якоїсь мови, це буде видно в `warnings` результату JSON; додайте точну назву
статті для цієї мови в `articles` і запустіть знову.

## Розробка й тестування

```bash
uv run ruff check .
uv run pytest -v          # юніт-тести, фікстури + синтетичні дані, без мережі
uv run pytest -m live     # опційно: живі виклики до реального Wikimedia/Wikidata API
```

## Як це перевірялося

- **Перевірка на чистому клоні**: `uv sync && uv run ruff check . && uv run
  pytest` на чистому клоні — 0 зауважень лінтера, 42/42 тестів проходять.
- **Коректність метрик на синтетичних даних**: стійке зростання, один великий
  сплеск, чиста сезонність, відоме лінійне падіння (перевірене проти точного
  очікуваного нахилу), молода стаття, неоднорідна кошик статей, закоротке
  вікно — кожен перевірений на конкретні очікувані числа.
- **Регрес-тест на реалістичному шумі**: зміна формули `spike_share` у Фазі 2
  була впіймана під час рев'ю, бо хибно позначала звичайні шумні дані як
  "домінування сплесків" (перевірено: ~0.38 замість правильних ~0.02–0.04);
  формулу відкотили назад, і тест з гаусівським денним шумом плюс кілька
  справжніх сплесків тепер стежить, щоб цей регрес не повторився непомітно.
- **Рубрика надійності**: один тест на кожне правило, кожен побудований на
  реальному виводі `metrics.analyze_topic()`, а не на вручну складених
  словниках.
- **Один живий наскрізний запуск**: "Астрономія" на `uk.wikipedia`, перевірено
  вручну — PDF на одну сторінку, кирилиця відображається коректно, цифри у
  звіті збігаються з JSON.
- **Ще не зроблено**: пооб'єктна звірка з веб-інструментом Wikimedia Pageviews
  Analysis (pageviews.wmcloud.org) для того самого вікна.

## Які AI-інструменти використовувалися і як перевірявся їхній результат

У проєкті задіяно п'ять AI-інструментів, кожен у своїй ролі, під координацією
розробника.

- **Розробник** виступав оркестратором: вирішував, який інструмент відповідає
  за яку частину роботи, з'єднував результати між ними (наприклад, переносив
  специфікацію з плану одного архітектора у виконання іншим), вручну запускав
  і перевіряв вивід тестів та живих CLI-запусків, а не довіряв власному
  підсумку інструмента, і власноруч правив деякі файли напряму (конфіги,
  прибирання зайвих файлів, дрібні фікси), коли це було швидше й безпечніше,
  ніж ще одна ітерація промпту.
- **Claude (чат)** виступав головним архітектором і рев'юером коду більшу
  частину розробки: писав специфікацію метрик і надійності, перевіряв дифи,
  витягнуті напряму з цього публічного GitHub-репозиторію (а не з підсумків
  самого кодового агента), перш ніж їх приймати, і саме так впіймав кілька
  реальних багів — `dict` там, де очікувався `int`; жирний кириличний шрифт,
  який ніколи не реєструвався і ламав генерацію PDF; забутий імпорт видаленого
  модуля, який зламав би команду `run`; надто вузьку колонку таблиці для
  українських підписів; і статистичний регрес (див. `spike_share` вище),
  внесений змінами іншого AI, впійманий лише через обчислення метрики на
  реалістичних синтетичних даних, а не довіру до того, що тести проходять.
- **ChatGPT** виступав другим архітектором на пізнішому етапі роботи,
  підготувавши `IMPLEMENTATION_PLAN.md`, `ARCHITECTURE_DECISIONS.md`,
  `PROJECT_STATUS.md` та `AGENT_HANDOFF.md`, щоб передавати кодовому агенту
  чітко окреслені, перевірювані фази роботи.
- **Grok** і **Gemini** залучалися на окремих етапах багато-AI співпраці (див.
  `ARCHITECTURE_DECISIONS.md`, ADR-006) поряд з Claude і ChatGPT як додаткові
  архітектори/рев'юери окремих рішень.
- **Claude Code**, працюючи через безкоштовні моделі, проксійовані через
  [Free Claude Code](https://github.com/Alishahryar1/free-claude-code)
  (переважно `nemotron-3-super-120b-a12b` від NVIDIA NIM, з фолбеками на
  Gemini/OpenRouter), писав і допрацьовував реалізацію за специфікаціями
  архітекторів.

Кожен етап перевірявся однаково, незалежно від того, який AI його
запропонував: автоматичні тести з конкретними очікуваними значеннями, `ruff`,
і запуск на чистому клоні. Самозвіти агентів неодноразово виявлялися
неповними або неточними (тести, що не покривали заявлене, "виправлення", яке
залишало другу точку виклику зламаною, твердження "no issues" від лінтера,
спростоване чистим середовищем) — це вдавалося впіймати лише витягуючи
реальний код з GitHub і читаючи або запускаючи його, тому розділ "перевірено"
вище перелічує конкретні перевірки, а не переказує підсумок якогось агента.

## Roadmap

- **Наступний крок**: рейтинг між мовами та спільний порівняльний графік, коли
  в `languages` більше одного елемента (наразі кожна мова аналізується й
  звітується незалежно).
- **v2**: пошук пов'язаних тем через граф категорій Wikipedia; рейтинг
  кількох тем в одному звіті.
- **v3**: заміна JSON-кешу на URL на DuckDB/Parquet для агрегації більшого
  масштабу; паралелізація запитів у межах лімітів Wikimedia; підтримка
  обробки на основі дампів для історії, глибшої за вікно зберігання API.
- **v4**: звірка із зовнішніми сигналами (наприклад, пошукові тренди);
  кореляція з власною аналітикою продукту користувача, якщо надана; плановий
  моніторинг зі сповіщеннями про суттєві зміни тренду.
