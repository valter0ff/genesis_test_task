# Аналізатор зацікавленosti Wikipedia

Самодостатня навичка агента для аналізу переглядів Wikipedia across language editions, щоб допомогти founders B2C-додатків вирішити, які теми та мови варто інвестувати.

## Огляд

Цей інструмент отримує дані про перегляди Wikipedia, обчислює нормалізовані метрики (річний річний зрост, нахиил схиль, udział спайків тощо), оцінює надійність і генерує односторонній PDF-звіт з графіками та таблицею підсумків. Розроблений для використання AI-агентами (наприклад, Claude Haiku) через простий CLI, проте також може використовуватися розробниками напряму.

**Ключові особливості**:
- Визначення назв тем до назв статей Wikipedia в різних мовах (через Wikidata або пошук per‑wiki).
- Отримання щоденних даних про перегляди (кешування для уникнення зайвих викликів API).
- Обчислення метрик точно за специфікацією: `yoy_norm`, `trend_pct_per_year`, `spike_share`, об'єм, прапорці надійності та впевненість.
- Генерація спільно käytвевого звіту A4 у форматі PDF з порівняльним графіком, таблицею метрик та розділом про припущення та обмеження.
- Підтримка ітеративних následних запитів (наприклад, «додати чеську», «прокинути вікно до 3 років») без повторного отримання кешованих даних.
- Немає скомпільованих бінарних файлів; середовище Python, яке можно відтворити, керується `uv`.

## Встановлення

1. Склонуйте репозиторій (або скопіюйте каталог навички).
2. Перейдіть до каталогу навички:
   ```bash
   cd wikipedia-interest
   ```
3. Синхронізуйте віртуальне середовище та встановіть залежності:
   ```bash
   uv sync
   ```
   Це встановлює залежності виконання (`requests`, `numpy`, `matplotlib`, `fpdf2`) та інструменти розробки (`pytest`, `ruff`).

## Використання

### CLI-команди

Точка входу — `wikitrends` (запускайте з `uv run wikitrends <command>` з каталогу навички).

| Команда | Призначення |
|---------|-------------|
| `fetch` | Завантаження щоденних даних про перегляди для даного проекту (видання мови) та назви статті. |
| `analyze` | Обчислення метрик з кешованих даних про перегляди. |
| `report` | Генерація одностороннього PDF-звіту з проаналізованих даних. |
| `run --spec spec.json` | Одноразове виконання: resolve → fetch → analyze → report за допомогою специфікації JSON. |

Кожна команда виводить один об'єкт JSON у stdout (журнали йдуть у stderr) з:
- `ok`: булеве значення, що вказує на успіх.
- `data`: результат, специфічний для команди.
- `warnings[]`: масив простих мовних повідомлень.
- `next_step`: підказка для наступної команди.

Коди виходу: `0` (успіх), `2` (неправильний ввід), `3` (проблема даних/API).

### Приклад робочого потоку

Припустимо, ви хочете порівняти зацікавленість у «йога» англійській, французькій та німецькій Wikipedia за останні 24 місяці.

1. **Створіть файл специфікації** (`spec.json`):
   ```json
   {
     "topic": "Yoga",
     "languages": ["en", "fr", "de"],
     "window": ["20210901", "20230831"],
     "criteria": {}
   }
   ```

2. **Запустіть навичку**:
   ```bash
   uv run wikitrends run --spec spec.json
   ```
   Інструмент виконає:
   - Визначить «yoga» до назв статей у кожній мові (через Wikidata sitelinks, з резервним варіантом пошуку).
   - Отриматиме щоденні перегляди для кожної розв'язаної статті (з кешуванням відповідей).
   - Обчислить метрики та vytvoříть оцінку надійності.
   - Згенерує `report.pdf` у робочому каталозі.

3. **Прочитайте вихід**:
   - Перевірте фінальний JSON на наявність `ok`: true та знайдіть згенерований PDF.
   - Відкрийте `work/<slug>/report.pdf`, щоб побачити вердикт, графік, таблицю та припущення.

### Непряме ланцюговое виконання (для просунутих користувачів)

Якщо ви предпочитаєте запускати кожен крок вручну:

```bash
# Отримати дані для англійської Wikipedia
uv run wikitrends fetch --project en.wikipedia --article Yoga --start 20210901 --end 20230831
# -> поверне JSON з next_step: "Run 'wikitrends analyze' to compute metrics from this data."

# Аналізувати (використовує робочий каталог з команди fetch)
uv run wikitrends analyze
# -> поверне JSON з next_step: "Run 'wikitrends report' to generate a PDF summary."

# Звіт
uv run wikitrends report
# -> поверне JSON, що підтверджує генерацію PDF.
```

## Розробка та тестування

- **Лінтинг**: `uv run ruff check .`
- **Тести**: `uv run pytest -v`
  - Модульні тести використовують записані фікстури; немає викликів мережі.
  - Щоб запустити живі тести API (необов'язково): `uv run pytest -m live`
- **Підказки типов**: Через всю кодову базу; можна додати mypy за бажанням.

## Ітеративні плани покращення (Дорожня карта)

На вимогу вимог, ось можливі еволюції без зміни основного контракту навички:

### v2: Виявлення пов'язаних тем
- Використовуйте граф категорій Wikipedia або «які ссилки тут ведуть», щоб пропонувати пов'язані теми (наприклад, для «йога», показати «медитація», «пілатес»).
- Ранжирування багатьох тем: обчисліть kompozційний бал зацікавленості по кластеру тем, щоб інформувати про більш широкі инвестиції в контент.

### v3: Масштабування до великих корпусів
- Заміна кешу JSON на DuckDB/Parquet для ефективних агрегацій багатьох статей та мов.
- Паралелізуйте отримання даних у межах обмежень швидкості Wikimedia (з урахуванням `User-Agent` та backoff).
- Підтримка обробки дампів для історичного аналізу поза межами зберігання API.

### v4: Додаткові сигнали
- Інтегруйте Google Trends (через `pytrends`) або сигнали соціальних медіа для триангуляції зацікавленosti Wikipedia.
- Включіть аналітику, специфічну для продукту (якщо надано користувачем), щоб коррелювати зацікавленість з конверсією.
- Моніторинг за розкладом: відстежуйте тенденції зацікавленості із часом та сповіщайте про значущі зміни.

## Верифікація та обмеження

- **Верифіковано на**: macOS/Linux з Python 3.11+, `uv` 0.4.x.
- **Протестовано моделей**: Вихіди CLI валідувалися з синтетичними фікстурами; кінцеві запуски перевірялися проти веб-інструменту аналізу переглядів Wikipedia для кількох реальних тем.
- **Обмеження** (завжди присутні в звітах):
  - Зацікавленість Wikipedia вимірює увагу, а не готовність платити або використання продукту.
  - Дані обмежені `agent=user` (виключають павуків та автоматизований трафік).
  - Нормалізація знімає тенденції платформи-wide, але не kontrollує за демографічними відмінностями редакторів між.language-изданиями.
  - Аналіз використовує лише повні календарні місяці; неповні місяці відкидаються.
  - Дивіться `references/limitations.md` для вичерпних деталей.
